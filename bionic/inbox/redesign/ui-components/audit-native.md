# Audit C: native (Swift) UI surface

Scope: `apps/studio-shell` (targets StudioShellCore, StudioShellEngine, studio-shell, StudioShellTests) and `apps/capture-companion/macos`. Read-only; facts with file:line (paths relative to `apps/studio-shell/Sources/studio-shell/` unless noted).

## Bottom line

The native surface is tiny and contains **no buttons, chips, toggles, labels-with-style, or SwiftUI**. A grep for `SwiftUI` and `NSButton` across both packages returns nothing. Every panel body (toolbar, strip, cards, footer, menus, toasts-in-page, the "Resume session" buttons) is web content in a `WKWebView` (the compact and Settings windows, and the main Studio window). The native code draws: window chrome, a few invisible drag/resize hit views, one translucent toast panel, the menu-bar status item and its menu, the app menu bar, and two modal `NSAlert`s. `capture-companion/macos` has no UI at all: it is a CLI (`Sources/capture-companion/Commands.swift:11-20` uses `print`, a stdin prompt flow). The commit-log phrases "native strip"/"native footer" refer to web components in the native-hosted panel, not Swift views.

## 2. Organisation

- `apps/studio-shell/Package.swift:1-72`: Swift 6 tools, macOS 14. Targets: **StudioShellCore** (Sources/StudioShellCore, pure Swift 6, no AppKit view code except small helpers: 20 files, decisions and wire contracts), **StudioShellEngine** (Sources/studio-shell/Engine, the hands-free engine, excluded from the executable target at :52), **studio-shell** (executable, Swift 5 mode `:54`, all AppKit), **StudioShellTests** (executable harness; Command Line Tools have neither XCTest nor Swift Testing, :9-11). It depends by path on `../capture-companion/macos` (CaptureCore, CaptureAdapters).
- Folders under `Sources/studio-shell`: flat files (AppDelegate, StatusMenu, StudioPanel, ConnectPrompt, StudioWebView, BridgeHandler, ShellModel...), `Presentation/` (NativeSurface 573 lines holding six classes, HitRegionTracker), `Engine/`. There is no `Views/`, `Components/` or `Theme/` folder.
- Reusable helpers that exist: `StatusMenu.add(...)` (:136), `ConnectPrompt.field/label` (:46,52), `ResizeHandle.Edge` geometry, `ToastLayout`/`PanelLayout` constants in Core. No style helper, no colour/font token file.
- Duplicated styling: negligible: two `NSTextField` label setups (ToastPresenter :446-447/467-471, ConnectPrompt :52-56), two NSAlert constructions, `NSColor.secondaryLabelColor` used twice. All are system colours/fonts, not brand.
- Hard-coded values mirroring web tokens: **none found**. No hex, no `--ov-*`/`--pn-*` equivalents. Native uses system semantic colours (`systemGreen`, `systemRed`, `secondaryLabelColor`, black/white in the toast). The only shared numbers are geometry, and they are mirrored the other direction: toolbar width 760 (PanelLayout.swift:18) must match the web toolbar, and `HitRegions` limits mirror `packages/interview-contracts` (HitRegions.swift:9, 28-30).

Dependency direction is one-way and narrow: only the containers (`.pn-pill`, `.pn-single-foot`, the typing list, HIT_SELECTORS) matter. A **button component can change its own class names freely** provided it keeps `<button>`/`[role=button]`/`[disabled]`/`[aria-disabled]`/`data-no-drag` semantics (the probe keys off tag/role, not `.pn-bar-button` etc.).

## 4. Recommendations

### (1) Is a Swift components layer warranted? No.
There are zero native buttons, chips, toggles or SwiftUI views. The visible native pieces are: a menu (system styled), two system alerts, one toast, and invisible handles. A `Components/` layer with ButtonStyle/ChipView/design-token Swift file would be speculative infrastructure with no consumer (AGENTS.md rule 1, ADR-0002). A token file mirroring `--ov-*`/`--pn-*` has nothing to theme: the only coloured native pixels are the toast gradient/white text and the status dot, and the web design is intentionally unreachable from AppKit (panels are web pages that paint their own tint). **Native "component reuse" is delivered entirely by the web component** because the Resume strip/footer/session buttons are web. Slice 5 in the plan ("native wrappers and any AppKit controls") should be reduced to: verify, and keep the native lists in step.

Honest caveats if the owner still wants consolidation: (a) at most extract the `ToastPresenter` look (30/19 pt fonts, 0.78 gradient, white) into a single private `enum ToastStyle` in NativeSurface.swift (about 6 lines, already one place); (b) delete dead `ToolbarDragView` (:405-427) and the unused `DragHandle` grip drawing (:432-437, only caller sets `showsGrip=false`); (c) split NativeSurface.swift (573 lines, six types) into `PanelWindow.swift`, `Handles.swift` (DragHandle, ResizeHandle), `ToastPresenter.swift`, which is organisational, not a component layer. These are optional cleanups, not part of the button work.

### (2) Folder organisation and button wrapper API
Not proposed, since no native buttons exist. If one ever appears (for example a native Settings control or the consent dialog replaced by a custom panel), the cheap trigger is a second implementation: then add `Sources/studio-shell/UI/` with `ButtonStyle.swift` (enums `Variant {primary, secondary, destructive, ghost}`, `Size {sm, md}`, `State {normal, disabled, loading}` as plain Swift values) and one `StyledButton: NSButton` applying them, with its colours defined in one `Theme.swift`. Until then, the web `Button` is the single component, and the Swift side should not mirror it. NSAlert and NSMenu items must remain system controls; they should not be restyled.

### (3) Risks and test impacts
- The web button refactor touches the native code only through the lists in section 3; no Swift change is required if `.pn-pill`, `.pn-single-foot`, the typing classes and HIT_SELECTORS keep their names and the new button renders as `<button>`.
- If a refactor changes tag/role (for example a `<div role=...>`-less clickable, or an `asChild` anchor without `href`: `pressable` has `a[href]` only, WindowDrag.swift:35) the cursor becomes grab/arrow and the press becomes a window drag. Anchors rendered via `asChild` must carry `href` or `role=button`.
- A disabled-by-`aria-disabled` or `disabled` attribute is what makes the probe answer arrow (:53): the component's loading/disabled state must keep setting one of those.
- Tests: `Tests/StudioShellTests/WindowDragTests.swift` (string contains checks on the probe script), `HitRegionTests.swift` (decode and geometry; no class names), `PresentationTests.swift` (state), plus the web guards `hit-regions.test.tsx`, `glass-guard.test.ts` and `single-panel.test.tsx`. None test Swift view construction; AppKit views are untested (the harness runs `StudioShellCore`/`Engine` logic only).
- `pnpm verify` runs `scripts/verify-native.mjs`: `swift build` and `swift run studio-shell-tests` for studio-shell, then `swift build` and `swift run capture-core-tests` for the companion; it skips off macOS or without `swift`. So a web-only slice does not exercise native build unless Swift files change; if a slice edits `WindowDrag.swift`, add or adjust its WindowDragTests assertion in the same change.
- A Swift change needs a native reinstall (`scripts/bundle-app.sh`) to be seen on the real app; web changes need the Docker web rebuild only.

## Ranked summary of native-side actions
1. No Swift work for the button/component consolidation; keep the class/selector lists unchanged.
2. Optional hygiene: delete dead `ToolbarDragView`; collapse `DragHandle` to the invisible strip it is used as; split `NativeSurface.swift` by type.
3. Add a one-line note to the web component docs: controls must render as `<button>`/`[role=button]`/`a[href]` with `disabled` or `aria-disabled` for disabled state, because WindowDrag keys off them.
